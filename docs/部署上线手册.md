## 二、最容易踩的坑：镜像必须导入 containerd

两个 Deployment 的 `imagePullPolicy` 都是 **`Never`**。这意味着 kubelet **不会去 Harbor 拉**，
它只在 **containerd 的 `k8s.io` 命名空间**里找镜像。

而 `docker build` 只把镜像放进 **Docker 自己的镜像库**。两者是**两套存储**。

> 只 `docker build` + `kubectl set image` → Pod 报
> `ErrImageNeverPull: Container image ... is not present with pull policy of Never` → **服务直接中断**。
> （2026-09-14 上线时就踩了这个，API 停了约 4 分钟，靠临时 `ctr import` 救回来。）

所以每次构建完，**必须**做这一步：

```bash
docker save <完整镜像名:tag> -o /tmp/img.tar
ctr -n k8s.io images import /tmp/img.tar
rm -f /tmp/img.tar            # 别把镜像 tar 留在磁盘上（单个数百 MB）
ctr -n k8s.io images ls -q | grep <tag>   # 确认已导入
```

## 三、标准上线流程

### 第 0 步：备份（服务器上）

```bash
mkdir -p /root/zhishu-mingxi-backups/<日期>-<改动名>
kubectl -n zhishu-mingxi get deploy zhishu-mingxi-api -o yaml > /root/zhishu-mingxi-backups/<日期>-<改动名>/deploy-api-before.yaml
kubectl -n zhishu-mingxi get deploy zhishu-mingxi-web -o yaml > /root/zhishu-mingxi-backups/<日期>-<改动名>/deploy-web-before.yaml
kubectl -n zhishu-mingxi get deploy -o custom-columns=NAME:.metadata.name,IMAGE:.spec.template.spec.containers[0].image
```

记下**当前两个镜像 tag**，这就是回滚目标。

### 第 1 步：确定改动范围 —— 只覆盖改动文件，**不要整棵覆盖**

**仓库 ≠ 线上。** 线上 api 镜像里只有 `backend/`（79 个 `.py`），而且其中若干文件和仓库版本不一样。
2026-09-14 实测（`live` 为线上容器、`repo` 为本地仓库）：

```
backend/api.py                        live=1e3a6ead…  repo=0b2aa74e…
backend/auth/dependencies.py          live=9253eb2a…  repo=bfb12b79…
backend/auth/models.py                live=b8c363af…  repo=2a81e790…
backend/auth/service.py               live=f919ec62…  repo=92989f08…
backend/compat.py                     live=40174489…  repo=b87ea847…
backend/learning/database.py          live=d0d91018…  repo=a7be7e56…
backend/management/auth.py            live=7c57d55a…  repo=82e8c3d0…
backend/management/teacher_service.py live=19705b98…  repo=7703bfe5…
```

**整棵 `backend/` 覆盖 = 把线上没在跑的那批改动一起推上线。**

> 每次上线前**自己重跑一遍**下面的比对，不要照抄上面这张表（表会过时）：
> ```bash
> POD=$(kubectl -n zhishu-mingxi get pod -l app.kubernetes.io/name=zhishu-mingxi-api -o jsonpath='{.items[0].metadata.name}')
> kubectl -n zhishu-mingxi exec $POD -- sh -c "cd /app && find backend -type f -name '*.py' | sort | xargs md5sum" > /tmp/live.txt
> # 再和本地仓库逐个 md5 对比，确认本次要改的文件是不是"线上就是仓库版"；不是就只能 overlay 覆盖本次改的，绝不能整棵覆盖
> ```

正确做法：用 **overlay Dockerfile**，`FROM` 当前线上那一版镜像，只 `COPY` 本次改的文件。

示例（某次只改了 3 个后端文件）：

```dockerfile
FROM 115.175.38.106:8079/zhishu-mingxi/api:<当前线上 tag>
USER root
COPY api/models.py       /app/backend/management/models.py
COPY api/exam_service.py /app/backend/management/exam_service.py
COPY api/router.py       /app/backend/management/router.py
RUN chown -R 10001:10001 /app/backend/management
USER 10001
```

前端同理：

```dockerfile
FROM 115.175.38.106:8079/zhishu-mingxi/web:<当前线上 tag>
USER root
COPY web/app.js     /usr/share/nginx/html/app.js
COPY web/index.html /usr/share/nginx/html/index.html
RUN chown 101:101 /usr/share/nginx/html/app.js /usr/share/nginx/html/index.html
USER 101
```

> 前端镜像的站点根是 **`/usr/share/nginx/html`**，容器里没有 `/textbook` 之外别的坑；
> `index.html` 里 `<script src="app.js?v=NN">` 的版本号**必须一起改**，否则浏览器继续用缓存旧 `app.js`。

### 第 2 步：构建 + 推 Harbor + 导入 containerd

```bash
cd /root/zhishu-mingxi-<改动名>-<日期>
docker build --no-cache -f Dockerfile.api -t 115.175.38.106:8079/zhishu-mingxi/api:<新 tag> .
docker build --no-cache -f Dockerfile.web -t 115.175.38.106:8079/zhishu-mingxi/web:<新 tag> .

# 构建产物自检（强烈建议）：文件名 + 内容哈希 + 关键函数是否在里面
docker run --rm --entrypoint sh <新 api 镜像> -c "md5sum /app/backend/management/*.py | head; id"
docker run --rm --entrypoint sh <新 web 镜像> -c "md5sum /usr/share/nginx/html/app.js /usr/share/nginx/html/index.html; grep -o 'app.js?v=[0-9]*' /usr/share/nginx/html/index.html"

docker push 115.175.38.106:8079/zhishu-mingxi/api:<新 tag>
docker push 115.175.38.106:8079/zhishu-mingxi/web:<新 tag>

# 关键一步：导入 containerd（见第二节）
docker save 115.175.38.106:8079/zhishu-mingxi/api:<新 tag> -o /tmp/api.tar && ctr -n k8s.io images import /tmp/api.tar && rm -f /tmp/api.tar
docker save 115.175.38.106:8079/zhishu-mingxi/web:<新 tag> -o /tmp/web.tar && ctr -n k8s.io images import /tmp/web.tar && rm -f /tmp/web.tar
```

### 第 3 步：切流量（**先前端一直没变，先 API 再 Web**）

```bash
kubectl -n zhishu-mingxi set image deploy/zhishu-mingxi-api api=115.175.38.106:8079/zhishu-mingxi/api:<新 tag>
kubectl -n zhishu-mingxi rollout status deploy/zhishu-mingxi-api --timeout=300s

kubectl -n zhishu-mingxi set image deploy/zhishu-mingxi-web web=115.175.38.106:8079/zhishu-mingxi/web:<新 tag>
kubectl -n zhishu-mingxi rollout status deploy/zhishu-mingxi-web --timeout=300s
```

顺序的理由：新后端对旧前端**无感**（旧前端不会调新接口），所以先上后端没有窗口期风险；
新前端一上去就会调新接口，所以**前端必须在后端之后**。

> `zhishu-mingxi-api` 的滚动策略是 `maxSurge:0 / maxUnavailable:1` + 单副本 →
> **切 API 时会有几十秒到几分钟的短暂不可用**，属正常。`web` 是默认策略，会先起新 Pod，基本无感。

### 第 4 步：验收

```bash

curl -s http://192.168.0.244:32170/openapi.json -o /tmp/oa.json
python3 -c "import json;d=json.load(open('/tmp/oa.json'))['paths'];print(len(d));print(sorted(d))"

# 4.2 健康 + 关键既有接口（期望 401/405/200，绝不是 404）
for p in /api/health /api/exam/generate /api/class/create /api/admin/teachers /api/kb/structured-questions; do
  printf "%-38s %s\n" "$p" "$(curl -s -o /dev/null -w '%{http_code}' http://192.168.0.244:32170$p)"
done

# 4.3 前端确实是新版
curl -s http://192.168.0.244:32170/index.html | wc -c
curl -s "http://192.168.0.244:32170/app.js?v=NN" | wc -c
```

再在浏览器里过一遍：登录 → 问答 → 练习/批阅 → 图谱 → 教材 → 教师端（班级/考试/备课）。
**验收脚本只读、不写数据**，可以在线上直接跑（如交付包里的 `验收.py`）。

### 第 5 步：记录

把本次 tag、改动文件、验证结论写进 `docs/` 或交付包里，并把服务器上的构建目录留下
（`/root/zhishu-mingxi-<改动名>-<日期>`），下次 overlay 的 `FROM` 就用这次的 tag。

## 四、回滚

```bash
# 方式一：直接切回上一版镜像（最快，镜像还在本地/containerd 里）
kubectl -n zhishu-mingxi set image deploy/zhishu-mingxi-api api=115.175.38.106:8079/zhishu-mingxi/api:<旧 tag>
kubectl -n zhishu-mingxi set image deploy/zhishu-mingxi-web web=115.175.38.106:8079/zhishu-mingxi/web:<旧 tag>
kubectl -n zhishu-mingxi rollout status deploy/zhishu-mingxi-api --timeout=300s

# 方式二：撤销滚动
kubectl -n zhishu-mingxi rollout undo deploy/zhishu-mingxi-api
kubectl -n zhishu-mingxi rollout undo deploy/zhishu-mingxi-web
```

若连 containerd 里都没有旧镜像，再 `docker save` + `ctr -n k8s.io images import` 一遍。

---

## 五、绝对不要做的事

1. **不要 `kubectl delete` / `kubectl apply` 整个集群或别的命名空间** —— 这台机器是老师的 k8s 节点。
2. **不要整棵覆盖 `backend/`** —— 会顺带推上 6 个被叫停的文件（见第 1 步）。
3. **不要只 `docker build` 就 `set image`** —— 必须 `ctr -n k8s.io images import`（见第二节）。
4. **不要动 `/state/learning.db` 的结构**，也不要在没备份的情况下写数据。
5. **不要把 API Key / 超管口令写进仓库或交付包**。运行时密钥在 Secret `zhishu-mingxi-runtime` 里。
6. 不要用 `:latest` 之类会漂移的 tag，**每次上线一个新 tag**。
